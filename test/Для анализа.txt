================================================================================
1. ЧТО ЭТО ЗА ПРОЕКТ
================================================================================

Инструмент получает список адресов сайтов и делает пассивный аудит: заголовки
безопасности, TLS-сертификат, TTFB, вес HTML, сторонние скрипты, perimeter SEO
(robots.txt, sitemap.xml, canonical, title, description, h1), политики
SPF/DMARC, CAA, MTA-STS, доступность разметки (alt, подписи полей, viewport),
мягкую 404 и редирект HTTP→HTTPS. Результат — один self-contained HTML-файл с
приоритетами «что чинить первым».

Код есть с 16.11.2026, зависимостей ноль:
  - scripts/audit-collect.mjs — сбор фактов -> audit-report/audit_data.json;
  - scripts/mail-policy.mjs — разбор SPF/DMARC без сети (чистые функции);
  - scripts/audit-summary.mjs — «Выводы» локальной моделью -> conclusions.json;
  - templates/audit-report.html + scripts/audit-render.mjs — отчёт из JSON;
  - tools/check-docs.mjs — гейт документации;
  - .opencode/commands/audit.md — команда /audit (сбор + рендер, без активного
    сканирования и без внешних API);
  - входной материал — предложение внешней модели (Qwen), 14 453 байта, 268 строк.

Живой прогон 16.11.2026: https://www.ducasolutions.com/ — 36 находок
(15 ok, 16 warn, 4 fail: нет HSTS, нет CSP, нет h1, mixed content;
1 unknown: DNS-резолвер недоступен), 5 HTTP-запросов на адрес, ALPN h2,
отчёт 15 КБ, ноль внешних запросов.

Чего проект НЕ делает (зафиксировано): активное сканирование (SQLi/XSS),
нагрузочные тесты, краулинг всего сайта, веб-интерфейс, хранение истории в БД.

================================================================================
3. ТРИ ПРИНЦИПА (решения, влияющие на архитектуру)
================================================================================

1. Числа собирает код, текст пишет модель. TTFB, заголовки и сертификат не
   оцениваются моделью, а измеряются скриптом: два прогона сравнимы.
2. HTML-отчёт собирается из шаблона подстановкой, а не генерируется моделью.
   Причина: пример отчёта — 14 453 байта (≈5 тыс. токенов), лимит output в
   профиле модели — 4096 токенов, скорость 25–35 ток/с.
3. Модель пишет только раздел «Выводы» — не больше 300 слов, каждая
   рекомендация ссылается на id находки из JSON.

Пример находки (реальный прогон):
  {"id":"csp","level":"fail","check":"CSP",
   "message":"Content-Security-Policy отсутствует: нет защиты от внедрения скриптов",
   "evidence":"content-security-policy: —"}

Правила контракта:
  - поле присутствует всегда; не смогли измерить — null, а не отсутствие ключа;
  - findings[].evidence содержит конкретику (имя заголовка, значение, мс);
  - level только: ok | warn | fail | unknown;
  - unknown никогда не считается ok и в отчёте рисуется серым.
  - почта (SPF/DMARC/MX) на поддомене — unknown, а не fail: записи обычно живут на
    апексе, и чужой домен нельзя записывать в вину сайту; резолвер недоступен —
    тоже unknown (в evidence код ошибки), а не молчаливый ok.

Отказы (не роняют прогон), проверено 16.11.2026 на
https://nonexistent-domain-abc123xyz.invalid: error "dns", status null, exit 0.
Также: таймаут 10 с, редиректы > 5, ответ 403/429, отсутствие ключа API.
Код выхода: 0 — собрано всё; 1 — отчёт не прошёл проверки рендера; 2 — ошибка
аргументов.

Браузерные данные лежат отдельно (audit-report/browser_data.json) и в audit_data.json
не пишутся: рендер принимает их ключом --browser (AUD-14).

«Выводы» модели лежат отдельным файлом audit-report/conclusions.json
({meta:{model, generated_at, words, truncated, ids_cited, ids[], prompt_chars},
text}). Скрипт audit-summary.mjs отказывается писать файл, если модель не
сослалась ни на один id находки, и обрезает текст по 300 словам с флагом
truncated. Рендер подставляет текст и подпись «модель, N слов, M ссылок».

Что он проверяет:
  - все обязательные файлы на месте (документация, журнал, бэклог, срез);
  - каждый документ из docs/ упомянут в docs/README.md (карта) и существует;
  - каждый корневой .md упомянут в README.md;
  - каждый пункт бэклога содержит file:line или вывод команды («проверено»);
  - в бэклоге нет пункта без ID формата AUD-NN;
  - в журнале есть запись формата (Stage N — ДД.ММ.ГГГГ);
  - нет файлов-двойников (второй журнал) и нет .env;
  - нет незаполненных заготовок в документах;
  - .gitignore покрывает node_modules/, .env, /tmp/, /reports/, /audit-report/.

Не заведено: `--self-test` на фикстурах (AUD-10), CI (гейты локальные, как в двух
других проектах владельца), проверка ссылок в готовом отчёте глазами.

Браузерный прогон гейтом не является: Lighthouse, trace и network живут только
в живой сессии OpenCode (desktop), в CI их нет (AUD-14). Результат такого
прогона попадает в audit-report/browser_data.json и в отчёте помечается «вне CI».

================================================================================
6. ОГРАНИЧЕНИЯ
================================================================================

  - Только пассивные проверки. Активное сканирование и нагрузка — только с
    письменным разрешением владельца, и не в этом инструменте.
  - Внешние API (PageSpeed, Observatory, SSL Labs) видят только публичные
    адреса; localhost и внутренняя сеть проверяются локально.
  - Вежливость: 5 запросов на адрес (документ, robots.txt, sitemap.xml, проба
    404, проба http://), пауза 1 с между адресами, свой User-Agent с контактом,
    таймаут 10 с, ответ 403/429 — статус unknown без обхода.
  - Отчёт: один файл, ноль внешних ссылок и скриптов, ≤ 150 КБ, печать A4.
  - Секреты только в .env; в документации — имена переменных.
  - Ноль зависимостей на старте: fetch, node:tls, node:fs.
